# Reproducing the SPQR Rust→ProVerif analysis

This documents how to reproduce the ProVerif analysis of the SPQR ML-KEM-Braid
protocol whose protocol logic is **compiled from the Rust source**
(`src/v1/unchunked/`) by [hax](https://github.com/cryspen/hax), rather than
hand-transcribed. It records exact toolchain versions, the trust boundary
(what is generated vs hand-written vs vendored-and-modified), a two-level
reproduction recipe, the proven properties, and the known deviations being
upstreamed.

For the model's design see
[`extraction-model/README.md`](extraction-model/README.md); for the hand-written
reference model see [`handwritten/spqr-cka.pv`](handwritten/spqr-cka.pv).

The hax ProVerif backend lives in hax's **Rust engine**
(`rust-engine/src/backends/proverif.rs`), but extraction still runs its *import*
phase through the OCaml `hax-engine`, so the Rust engine and the OCaml engine
must be the **same** hax build (a version mismatch panics with "ocaml engine
crashed"). `proofs/proverif/setup-hax.sh` clones the pin, builds the Rust
binaries, and builds + installs the matching OCaml engine into the `hax-proverif`
opam switch; `hax.py` then locates that engine automatically, so no `opam env` is
needed (override with `$HAX_OPAM_SWITCH` / `$HAX_ENGINE_BINARY`).

## Trust boundary

The analysis verifies the protocol *as compiled from Rust*. The trusted hand-
written surface is confined to the cryptographic idealization:

| File | Origin | Trusted? |
|---|---|---|
| `extraction/lib.pvl` | **Generated** by hax from `spqr::v1::unchunked` (+ deps). Never hand-edited; byte-identity is checkable (see L2). | No — it is compiler output, reproducible. |
| `extraction-model/handwritten_lib.pvl` | Hand-written symbolic Dolev–Yao crypto (ML-KEM split, chaining-MAC authenticator) the generated code calls. | **Yes** — small, audited against the spec. |
| `src/*.rs` `replace_body`/`pv_extern` bodies (`cfg(hax_backend_proverif)`) | Hand-written symbolic bodies that map each crypto *leaf* onto `handwritten_lib.pvl`'s vocabulary. | **Yes** — same surface as above. |
| `extraction-model/model.pvl`, `reach.pv`, `conf.pv`, `auth.pv` | Hand-written adversary model (multi-epoch ping-pong, role swap, compromise) + security queries. | Standard for any ProVerif analysis. |
| `extraction-model/primitives.pvl` | hax's shipped prelude, **vendored with exactly 3 deviations** (see below). | Yes — deviations documented. |
| `extraction-model/nepochs.pvl` | The `NEPOCHS` bound (`max_epoch()`), regenerated by `verify-proverif epochs=N`. | n/a |

**Why the crypto is hand-modelled at all** (and why this *shrinks* the trusted
base vs the hand-written `spqr-cka.pv`): ML-KEM/HKDF/HMAC cannot be compiled to
ProVerif — they are idealized symbolically (the Dolev–Yao abstraction, shared by
*all* symbolic analyses including `spqr-cka.pv`). `replace_body` maps each Rust
crypto leaf onto a shared symbolic vocabulary whose `reduc` rules link the
symbols (`pkdec` inverts `pkenc1`/`pkenc2`; `ek_matches`; MAC-verify-by-equality)
and produce the structured returns the protocol destructures (`encaps1 →
(ct1,es,ss)`). Because **only the crypto leaves are hand-modelled and the whole
protocol state machine is compiled**, the trusted surface here is *strictly
smaller* than in the all-hand-written model — it is exactly the surface checked
for spec-faithfulness.

### `primitives.pvl` deviations from hax's shipped prelude

Three changes, all needed so integer-typed epoch comparison/arithmetic is
*decidable* in the symbolic model (otherwise generated `assert_eq!(epoch, …)`
guards never discharge and every recv transition dead-ends):

1. `nat_lit(nat): bitstring` → `… [data]` (projectable, so epoch arithmetic can reduce).
2. `machine_int__eq` / `machine_int__ne`: opaque `[data]` → reductive `letfun` (symbolic equality, same shape as `core__cmp__PartialEq__eq`).
3. `machine_int__add`: opaque `[data]` → reductive `letfun` for the `+ 1` case (the only arithmetic the protocol does; ProVerif `nat` supports only `x + constant`).

These are being upstreamed into hax's prelude (see *Upstreaming* below); (1)–(2)
are clean; (3) is under discussion. Until then they live in the vendored copy.

## Two-level reproduction

### L1 — verify the proofs (ProVerif only; no hax build)

Needs only ProVerif 2.05 and the committed files.

```
# Assert every ProVerif verdict against the documented expected results
# (PASS/FAIL report; exits non-zero on any mismatch):
python3 hax.py check-proverif epochs=4

# Or run a single property and read ProVerif's raw output:
python3 hax.py verify-proverif epochs=6 reach.pv    # reachability + key agreement
python3 hax.py verify-proverif epochs=6 auth.pv     # mutual authentication
python3 hax.py verify-proverif epochs=6 conf.pv     # confidentiality + forward secrecy
python3 hax.py verify-proverif epochs=6 sanity.pv   # non-vacuity controls
```

`check-proverif` compares each verdict to the `(* EXPECT: ... *)` annotation in
the query file and reports e.g. `14/14 verdicts match expected` (the EXPECT
annotations assume NEPOCHS >= 4). `verify-proverif` just runs ProVerif and prints
its output. Both take `epochs=N` (the NEPOCHS bound) and any number of query
files. (Equivalently, by hand, from `proofs/proverif/`: `proverif -lib
extraction-model/primitives.pvl -lib extraction-model/handwritten_lib.pvl -lib
extraction/lib.pvl -lib extraction-model/nepochs.pvl -lib
extraction-model/model.pvl extraction-model/<q>.pv`.)

### L2 — re-derive `lib.pvl` from Rust (build hax)

Establishes that the verified protocol is exactly hax's output of the SPQR
source:

```
# One-time: clone the pinned hax + install the Rust engine AND the matching
# OCaml hax-engine into the `hax-proverif` opam switch. Needs opam/node/jq (see
# the toolchain table); the OCaml engine build takes a few minutes.
proofs/proverif/setup-hax.sh                    # -> ./.hax-proverif by default
export HAX_PROVERIF_DIR=<dir printed by the script>

# hax.py resolves the matching OCaml engine from the hax-proverif switch itself
# (override via $HAX_OPAM_SWITCH / $HAX_ENGINE_BINARY) — no `opam env` needed:
python3 hax.py extract-proverif                 # regenerate extraction/lib.pvl
shasum -a 256 -c proofs/proverif/extraction/lib.pvl.sha256   # must match
```

Expected `lib.pvl` digest (SHA-256):
`51b54eed55ee23d19386f7a62fb68dbf3a25ef80d5567c77f86e1c8d20f6395b`
(also stored in `extraction/lib.pvl.sha256`).

### Regression (the SPQR refactors are behaviour-preserving)

```
cargo build      # clean: cfg(hax_backend_proverif) is unset, annotations inert
cargo test --lib # 52 tests pass
```

## What is proven

For the authoritative statement of what the ProVerif analysis establishes —
reachability, confidentiality with **forward secrecy**, and mutual authentication — and
its trust boundary, see [`../PROOF_STATUS.md`](../PROOF_STATUS.md). In
particular the forward-secrecy / post-compromise nuance (PCS heals from a KEM-key
compromise but **not** from an authenticator compromise), the `ek_matches` assumption,
and the CKA-only, bounded scope are documented there and are **not** duplicated here.

Reproduction-relevant facts about the query set (which live here rather than in the status
doc):

- The query set is the same as `spqr-cka.pv` (no simplification): reachability + key
  agreement, mutual authentication (both directions), and confidentiality.
- **Sound**: every query file uses only `nounif` (resolution-order only — always sound);
  no `restriction`/`axiom`, no induction lemmas.
- Both models verify all properties to **NEPOCHS=6** — each generated query in
  ~40–60 s / ~1.7 GB, `spqr-cka.pv` in ~2 min / 3.5 GB (48 GB machine).
- The compromise scenario (`model.pvl`) mirrors `spqr-cka.pv`'s: KEM keys compromised at
  alternating epochs + the responder authenticator at the last epoch, leaving other
  epochs' KEM keys intact so forward secrecy is tested non-trivially. `sanity.pv`
  confirms non-vacuity (compromised epochs leak; an uncompromised epoch between two
  leaking neighbours stays secret; no cross-epoch leakage; an authenticator-only
  compromise leaks via active MITM).

## Relationship with the hand-written model

The hand-written model (`spqr-cka.pv` + `cryptolib.pvl`) and this generated model
target the same protocol (the v1 ML-KEM Braid) and state the same security
queries. The points of difference:

- **Queries.** `reach.pv` / `conf.pv` / `auth.pv` use the same query formulas as
  `spqr-cka.pv` (same events, same implications, same `ep' <= ep` and `@i,@j,j<i`
  ordering), up to variable names and the split into one file per property — the
  queries are otherwise identical.
- **Protocol process.** Here it is compiled from `src/v1/unchunked` (hax output,
  `lib.pvl`); in `spqr-cka.pv` it is written by hand. The compiled process is
  in-order (header → ek → ct1 → ct2), matching the Rust state machine;
  `spqr-cka.pv` additionally models ct1 arriving before the ek is sent. Message
  reordering in the implementation is handled by the chunked layer, which is not
  modelled here.
- **Epoch-key KDF.** Both models derive the epoch key from the shared secret +
  epoch + label only (matching the spec's `KDF_OK` and Rust
  `kdf::derive_scka_secret`); transcript binding comes from the authenticator MAC
  chain, not the KDF. KEM split, MAC, and ek/header check are modelled the same in
  both.
- **Compromise.** `extraction-model/model.pvl` mirrors `spqr-cka.pv`'s fixed scenario
  (KEM keys at epochs 1/3 + a responder authenticator at epoch 4), mapped to this
  model's role-swap — the apples-to-apples comparison. The bound 6 leaves epochs
  5-6 uncompromised, exercising healing past the last (epoch-4) compromise.
- **Scope.** With `nounif` in every query file, both models (fixed compromise)
  verify all properties to NEPOCHS=6: each generated query in ~40-60 s / ~1.7 GB,
  and `spqr-cka.pv` in ~2 min / 3.5 GB.

## Known deviations & upstreaming

**hax ProVerif backend (file as issues; SPQR keeps source-level workarounds until fixed):**
- Struct construction uses source-literal field order but destructure/accessors
  use definition order → silent field swap (we write struct literals in
  definition order; see notes in `src/v1/unchunked/send_ct.rs`).
- `pv_extern` emits the call with the original Rust param name, but the engine may
  rename it (`secret` → `secret_kw`) → we rename the Rust param.
- `replace_body` on `&mut self`/unit methods discards the body value (returns the
  *old* self) → `Authenticator::update` made consuming (`self -> Self`).
- `replace_body` on `&mut rng`-threaded fns re-wraps `Tuple2(rng, body)` → the
  body returns only the inner value.

**hax prelude (`primitives.pvl`):** upstream the decidable `machine_int__eq/ne`
and `nat_lit [data]` (clean); discuss `machine_int__add` (GSVerif vs `+1`).

**SPQR:** the annotations are gated on `cfg(hax_backend_proverif)` — set only by
hax during ProVerif extraction, so normal builds and `cargo test --all-features`
never see them (no effect on normal builds);
the refactors are behaviour-preserving (52 tests pass). The only real API change
is `Authenticator::update` `&mut self` → `self -> Self`.
